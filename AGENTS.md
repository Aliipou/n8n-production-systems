# AGENTS.md

Binding rules for any AI coding agent (Cursor, Claude Code, Copilot) working in this repository. Read this file in full at the start of every session. If a chat instruction conflicts with this file, stop and ask the owner before acting.

- Owner: Ali Pourrahim (github.com/Aliipou)
- Repository: `n8n-production-systems` (monorepo)
- Master plan: `docs/PLAN.md`
- Specs: `docs/specs/00-platform.md` to `docs/specs/05-multi-tenant.md`
- Progress log: `docs/PROGRESS.md`
- Open questions: `docs/QUESTIONS.md`
- Ready-made session prompts: `docs/CURSOR_PROMPTS.md`

## 1. What this repository is

A set of production-style automation systems where n8n is the orchestration layer and small Python and Go services handle computation, state, and security-sensitive logic. The audience is freelance clients, hiring engineers, and the n8n community. Every project must run locally with one command, work offline with mock services, and document how it fails.

It is not a collection of toy workflows, a chatbot showcase, or a place to try new frameworks.

## 2. Session protocol

Start of session:
1. Read `AGENTS.md`, `docs/PLAN.md`, the spec of the current phase, and `docs/PROGRESS.md`.
2. Name the task ID you will work on (for example `P01-T04`). One task at a time.

During the session:
- Follow the task order in the spec unless a task is blocked.
- Do not start a new project until the current one meets the Definition of Done in `docs/PLAN.md` section 7.
- If the spec is ambiguous, contradictory, or looks wrong, add an entry to `docs/QUESTIONS.md` (date, task ID, question, options you see) and move to an unblocked task. Never guess on anything that changes architecture, data model, security, licensing, or public claims.
- If you are not certain how an n8n node, n8n CLI command, environment variable, or third-party API behaves in the pinned version, check the official documentation for that version. If you cannot verify, write `TODO(verify): <what, why>` in the code or doc and mention it in the commit message. Never invent node parameters, API fields, CLI flags, or header names.

End of task:
1. Run `make check`. Fix everything it reports.
2. Update `docs/PROGRESS.md`: task ID, date, what changed, known gaps.
3. Commit following section 8. Push only when `make check` passes.

## 3. Absolute rules

1. Never commit secrets: API keys, tokens, passwords, `N8N_ENCRYPTION_KEY`, webhook secrets, private keys, `.env` files. Only `.env.example` with placeholder values.
2. Never commit real personal data or real documents (real invoices, real emails, real people, real customer names). Use synthetic data generated by scripts in the repo (Faker with `fi_FI`, `sv_SE` and `en_US` locales). Company names in fixtures are invented and must not match real companies.
3. Never commit exported workflows that contain `pinData`, execution data, or credential values. All workflow JSON goes through `scripts/sanitize_workflows.py` and `scripts/lint_workflows.py` before commit.
4. Never invent numbers. Every latency, accuracy, cost, throughput, or recovery-time figure in a README or doc must come from a script in this repo that was actually run, with date, hardware, model name, and dataset recorded next to it. If a number does not exist yet, write "not measured yet".
5. Never make claims that are not true: no fake clients, no "used in production by", no "exactly-once", no "GDPR compliant" (write "designed with GDPR considerations; not legal advice"). Demo scenarios are labelled "reference implementation with synthetic data".
6. Never rewrite history on `main`, never force push `main`, never backdate commits, never create filler commits to inflate activity.
7. Never call paid APIs (LLM providers, enrichment providers, email providers) in CI or automated tests. CI uses the mock services.
8. Never bind n8n, databases, or internal services to `0.0.0.0` in the default compose files. Bind to `127.0.0.1`.
9. Never re-enable n8n features that 2.x disables for security (Execute Command node, environment access from Code nodes) to make something easier. Find another way or ask.
10. Never use `latest`, `next`, or unpinned image tags or dependency versions.
11. Never return a 2xx response to an external sender before its data is durably stored.

## 4. n8n rules

Version and setup
- n8n runs in queue mode (main plus at least 2 workers) on Postgres and Redis, using the exact version pinned in `platform/VERSIONS.md` (a stable 2.x release). Only features of the free self-hosted Community Edition may be used. Do not depend on Enterprise features (Variables, external secrets, log streaming, source-control environments, SSO).
- Before using any node, setting, or environment variable, confirm it exists and behaves as expected in the pinned version. n8n 2.x changed defaults (environment access from Code nodes blocked, Execute Command disabled, sub-workflows must be published to be callable). Read the official 2.0 breaking-changes page before Phase 0.

Workflow design
- n8n orchestrates: triggers, routing, integrations, human steps, notifications. Backends compute: scoring, validation, parsing, OCR, cryptography, tenant isolation, anything that needs unit tests or durable state. State this split in every README.
- One workflow, one responsibility. Soft limit 25 nodes, hard limit 40. Split larger flows into sub-workflows ("When Executed by Another Workflow" trigger with a defined input schema) called with Execute Workflow.
- Every workflow except the error handler itself has its Error Workflow setting pointing to `[PLT] Error Handler`.
- Webhook workflows validate input quickly, answer with an explicit status code (202 accepted, 200 duplicate, 400 invalid, 401 unauthenticated), and do heavy work after responding. No webhook without authentication (Header Auth credential, or HMAC verified by a backend).
- Every HTTP Request node has an explicit timeout, a descriptive name, and a deliberate error setting: either Retry On Fail for short transient retries, or the error output routed to classification. "Continue on fail" without handling the error is forbidden.
- Idempotency is enforced by a database unique constraint (`INSERT ... ON CONFLICT DO NOTHING RETURNING`), never by "select then insert", never by in-memory or static-data checks. Concurrent duplicates must produce exactly one side effect. Every project has a test for this.
- Never make an execution sleep for hours or days with a Wait node (follow-ups, reminders, long backoff). Store the due time in a table and pick it up with a scheduled workflow. Short waits (seconds) are fine.
- Do not pass binary files or large payloads through n8n. Pass IDs; the backend stores files.
- Do not pass secrets through node outputs. Anything a node outputs is saved in execution data. Secrets live in n8n credentials or in the backend.
- No hardcoded URLs, thresholds, email addresses, or channel names inside nodes. Use credentials, a settings table, or backend config.
- Naming: workflows `[P01] Lead Intake`, `[PLT] Error Handler`. Nodes are named by intent (`Validate payload`, `Upsert contact in CRM`), never default names such as `HTTP Request1` or `Code`.
- Each section of a canvas has a sticky note saying what it does and what can fail there. Canvas screenshots go into READMEs, so they must be readable.
- Code nodes: JavaScript, short, pure (no network calls). Any Code node logic longer than 15 lines lives in `code-snippets/<name>.js` with Vitest tests and is copied into the workflow by `make sync-snippets`. The linter fails when a Code node differs from its snippet.
- Logging: write structured events to `ops.execution_log` using the standard columns in `docs/specs/00-platform.md`. Every record has `correlation_id`, `project`, `workflow`, `execution_id`. Do not create a sub-workflow call per log line.

## 5. How workflow JSON gets into the repo

Hand-written n8n JSON from an AI agent often fails on import (wrong node type versions, wrong parameter shapes). Therefore:

1. Before building, write the workflow spec (trigger, nodes in order, inputs, outputs, error paths) in the project's `docs/workflows.md`.
2. Build the workflow in the running pinned n8n instance. Either the owner builds it in the editor, or the agent creates it through the n8n public API (API key in local `.env` only) or a tool that reads real node schemas from the running instance. The agent may draft JSON by hand only if step 3 then passes.
3. `make import P=<project>` into a clean local instance, publish or activate, and run the project's end-to-end tests. JSON that has not passed this step is never committed.
4. `make export P=<project>` (n8n CLI export, one file per workflow), which runs the sanitizer and the linter.
5. Commit the sanitized JSON. Workflow IDs stay stable because sub-workflow calls depend on them.

The linter fails on: `pinData` present, default node names, missing Error Workflow setting, HTTP Request without timeout, strings matching secret patterns, Code node differing from its snippet, more than 40 nodes, hardcoded `http://` or `https://` URLs outside credentials and the settings lookup.

## 6. LLM rules

- LLM output is never trusted directly. Every call uses a JSON schema (structured output). The result is validated; invalid output gets one retry that includes the validation error; after that the item goes to human review or a deterministic fallback.
- Use the LLM only where rules cannot do the job (intent, free text, messy documents). Scores, thresholds, totals, checksums, dates, and routing are computed in code with unit tests.
- The LLM contribution to any decision is capped (for example at most 20 of 100 score points). Document the cap in the README.
- Temperature 0 for classification and extraction. For every call record model, prompt version, input and output tokens, latency, and validity in the project's LLM table and in `ops.audit_log`.
- Prompts live in `prompts/<name>.v<N>.md`. Changing a prompt means adding a new version file, not editing the old one.
- All user-supplied text (form messages, emails, document text) is untrusted. The LLM in these pipelines has no tools with side effects. Every project that uses an LLM has a prompt-injection fixture and a test proving it changes nothing important.
- Never use the model's self-reported confidence as the confidence. Compute confidence from validators, evidence checks, and agreement with rule-based extractors.
- Provider access goes through an OpenAI-compatible base URL so CI points at `mock-llm`. Real providers are configured only in `.env`. If the pinned n8n credential cannot take a custom base URL, route the call through the project backend and record that in an ADR.

## 7. Code rules

Python (backends, mocks, scripts)
- Python 3.12, `uv`, `ruff` (lint and format), `mypy --strict` on `src/`, `pytest` with coverage, FastAPI, Pydantic v2, `psycopg` 3 with parameterized SQL. No ORM for core tables.

Go (ingress, dispatcher, exporter, CLIs, flaky-api)
- Go version pinned in `go.mod`, `golangci-lint`, `go test -race ./...`, standard library `net/http` where possible, `pgx` for Postgres, `log/slog` JSON logs.

JavaScript (Code node snippets only)
- Node LTS, Vitest, no dependencies inside snippets.

SQL
- Plain SQL migrations applied by `dbmate`: shared in `platform/db/migrations`, per project in `projects/<p>/db/migrations`. Each project owns its schema (`p01` ... `p05`); shared tables live in schema `ops`. Every table has `created_at`; tenant-scoped tables have `tenant_id`.

Docker
- Pinned tags (digests preferred for third-party images), non-root user in own images, healthcheck on every service, `depends_on` with `condition: service_healthy`.

General
- Configuration through environment variables, validated at startup; fail fast with a clear message.
- Structured JSON logs. Never log full payloads that can contain personal data; log IDs and types.
- No new languages, frameworks, or major libraries beyond `docs/PLAN.md` section 4 without an ADR approved by the owner.
- No dead code, no commented-out blocks, no placeholder functions that pretend to work, no `pass`-only handlers.

## 8. Git and GitHub rules

- Branch per task group: `feat/p01-intake`, `fix/p03-dispatcher-backoff`, `docs/p02-readme`. Open a pull request into `main` with the PR template filled in. If the owner asks for direct pushes to `main`, `make check` must still pass first.
- Conventional Commits: `feat(p01): add lead intake webhook`, `test(p03): cover concurrent duplicate delivery`, `docs(p02): add failure modes`. Scope is a project ID or `platform`, `ci`, `docs`.
- Small commits that each build and pass tests. List any `TODO(verify)` items in the commit body.
- Never commit `.env`, `node_modules`, virtualenvs, `__pycache__`, build output, n8n or database volumes, or files over 5 MB. Sample PDFs stay under 300 KB each; full datasets are generated by script, not committed.
- Pre-commit hooks: gitleaks, ruff, gofmt, workflow sanitize and lint.
- Tag each project when its Definition of Done is met: `p01-v1.0.0`.

## 9. Security and data rules

- Signature checks use the raw request body, constant-time comparison, and a timestamp tolerance where the provider supports it.
- Least privilege: each service has its own database role with only the grants it needs. `ops.audit_log` is append-only (no UPDATE or DELETE grants for any application role).
- Every table holding personal data has a documented retention period and a purge job.
- Unsubscribe and suppression lists are honoured by every email-sending path, with a test.
- CI scans dependencies and images (pip-audit, govulncheck, Trivy). High and critical findings block merge unless documented in `docs/security-exceptions.md` with a reason and a review date.

## 10. Testing rules

- Unit tests for all backend logic (scoring, validators, normalizers, signature verification, error classification). Table-driven where possible.
- End-to-end workflow tests in `projects/<p>/tests/e2e/`: start the stack, import and publish workflows, call webhooks, assert on database rows, Mailpit messages, and mock service state.
- Every row in a project's `docs/failure-modes.md` links to a test or a chaos script. A failure mode without one is not listed as handled.
- Mandatory in every project: concurrent duplicate test, invalid input test, dependency 500 test, dependency 429 test, dependency timeout test.
- Tests are deterministic: fixed seeds, mock LLM responses keyed by input hash, frozen time where needed. No sleeps longer than needed; poll with timeouts.

## 11. Documentation and writing style

- Each project README follows `docs/templates/PROJECT_README_TEMPLATE.md`. Sections cannot be removed; "not applicable" needs a reason.
- Diagrams as code (Mermaid in Markdown), also exported to `docs/architecture.png` with mermaid-cli.
- Architecture decisions go in `docs/adr/NNNN-title.md` (global) or `projects/<p>/docs/adr/` (project): context, decision, alternatives, consequences.
- Writing style for all docs, READMEs, commit messages, and PR text:
  - Plain and specific. Say what the system does, what it does not do, and how it fails.
  - No em dashes. Use commas, colons, parentheses, or separate sentences.
  - Banned words: passionate, leverage, cutting-edge, seamless, robust, revolutionize, game-changer, supercharge, unlock, delve, empower, next-level, world-class, state-of-the-art.
  - No decorative strings of adjectives, no emoji in headings, no marketing tone.
  - The Limitations section is honest and specific.

## 12. Stop and ask the owner when

- A task needs a paid account, a real API key, or spending money.
- A change affects security, the data model, public claims, or licensing.
- The pinned n8n version cannot do what the spec requires.
- You would need to disable a security default or add a language, framework, or service not in the plan.
- A test cannot be made deterministic.
- You are about to delete files you did not create in this session.
